### BUG-1 🔴 CRITICAL：Web 端 localStorage 代理脚本仅在主页面注入，子页面完全失效

**位置**：`MainActivity.kt` → `buildWebOverlay()` → `shouldInterceptRequest`（第 1634 行）

**问题描述**：
```kotlin
val isIndex = request.isForMainFrame &&
    (url.host == "127.0.0.1" || url.host == "localhost") &&
    (url.path.isNullOrEmpty() || url.path == "/" || url.path == "/index.html")
return if (isIndex) injectIndexShim(url) else null
```
`storageShimScript`（localStorage→宿主文件代理）**只在根路径（`/` 或 `/index.html`）注入**。  
dsh Web UI 打开插件管理页、设置页、引擎控制台等子路由后，`shouldInterceptRequest` 直接返回 `null`，代理脚本不生效。  
这些页面调用 `localStorage.setItem()` 时，WebView 原生存储若被禁用/配额超限则**静默失败**，用户配置完全丢失。

**触发场景**：
1. 用户在 Web UI 安装插件 → 插件尝试通过 localStorage 保存配置 → 写入失败（页面不在根路径）
2. 用户在 Web UI 修改背景/主题配置 → 保存后重启 Web 页，配置消失

**修复方案**：将拦截条件改为「所有来自本地引擎的 HTML 响应」，同时增加 Content-Type 校验防止污染非 HTML 响应：

```kotlin
override fun shouldInterceptRequest(
    view: android.webkit.WebView,
    request: android.webkit.WebResourceRequest,
): android.webkit.WebResourceResponse? {
    val isLocal = (request.url.host == "127.0.0.1" || request.url.host == "localhost")
    // 对本地引擎的所有 HTML 请求都注入 localStorage 代理
    return if (isLocal) injectIndexShim(request.url) else null
}
```

同时在 `injectIndexShim` 开头增加 Content-Type 检查，避免污染 API/JSON 响应：
```kotlin
private fun injectIndexShim(url: Uri): android.webkit.WebResourceResponse? {
    // ...现有引擎繁忙检测...
    conn = (java.net.URL(url.toString()).openConnection() as java.net.HttpURLConnection).apply {
        connectTimeout = 3000
        readTimeout = 5000
        setRequestProperty("Accept", "text/html, */*;q=0.8")
    }
    if (conn.responseCode != 200) return null
    // 新增：只处理 HTML 响应，跳过 JSON/API/静态资源
    val contentType = conn.getHeaderField("Content-Type")?.lowercase()?.orEmpty()
    if (!contentType.contains("text/html")) return null
    // ...后续注入逻辑...
}
```

### BUG-2 🔴 CRITICAL：无 MANAGE_EXTERNAL_STORAGE 权限时，SAF 目录选择器完全不触发

**位置**：`MainActivity.kt` → `pickDirectory()`（第 1241 行）

**问题描述**：
```kotlin
private fun pickDirectory() {
    if (Build.VERSION.SDK_INT < 30) {
        terminalScreen.terminal().appendLine("Android 10 及以下不支持选择外部目录")
        return
    }
    if (!android.os.Environment.isExternalStorageManager()) {
        showAllFilesAccessExplainDialog()  // 仅弹出说明对话框
        return  // ← 直接返回，不调用 directoryPicker.launch()！
    }
    directoryPicker.launch(null)  // 只有拥有权限时才走到这里
}
```
当用户没有「所有文件访问权限」时，函数只显示提示对话框后直接 `return`，**从未调用 SAF 的 `OpenDocumentTree` 选择器**。  
用户被困：既不能选目录，也没有直接进入系统设置的入口。

**修复方案**：移除权限前置检查，始终走 SAF 路径；权限检查移到选择完成后：

```kotlin
private fun pickDirectory() {
    if (Build.VERSION.SDK_INT < 30) {
        terminalScreen.terminal().appendLine("Android 10 及以下不支持选择外部目录")
        return
    }
    // 始终走 SAF 路径（不需要 MANAGE_EXTERNAL_STORAGE 权限）
    directoryPicker.launch(null)
}

// 在 directoryPicker 回调中补充提示
private val directoryPicker = registerForActivityResult(ActivityResultContracts.OpenDocumentTree()) { uri ->
    val term = terminalScreen.terminal()
    if (uri != null) {
        val path = AndroidBridge.resolvePickedPath(uri)
        prefs.edit().putString("workspace_dir", path).apply()
        term.appendLine("工作目录已选择: $path")
        // 如果路径在公共存储区，提示可能需要额外权限
        if (path.startsWith("/storage/emulated/0")) {
            term.appendLine("如需引擎直接读写该目录，请在设置中申请所有文件访问权限")
        }
        pendingPickCallback?.let { cb ->
            pendingPickCallback = null
            webView.evaluateJavascript(
                "window.__dshBridge && window.__dshBridge.onDirectoryPicked(" + jsString(cb) + ", " + jsString(path) + ")",
                null,
            )
        }
    } else {
        term.appendLine("已取消选择工作目录")
        pendingPickCallback?.let { cb ->
            pendingPickCallback = null
            webView.evaluateJavascript(
                "window.__dshBridge && window.__dshBridge.onDirectoryPicked(" + jsString(cb) + ", " + jsString("") + ")",
                null,
            )
        }
    }
}
```

### BUG-3 🟠 HIGH：公告拉取镜像回退在自动模式下完全无效

**位置**：`AnnouncementManager.kt` → `load()`（第 37-39 行）

**问题描述**：
```kotlin
val um = UpdateManager.forPrefs(context)
val resolved = um.activeMirror?.resolve(URL) ?: URL  // ← 当 activeMirror=null（默认自动模式）时，
                                                     //   resolved 等于原始 URL，fallback 等于重试同一地址
body = fetch(resolved)
```
默认情况下 `activeMirror` 为 `null`（自动测速模式），所以 `resolved` 恒等于原始 `URL`。  
官方直连失败后的「镜像回退」实际是**用同一个 URL 再请求一次**，对网络受限环境毫无意义。

**修复方案**：
```kotlin
if (body.isBlank()) {
    Logs.logE(context, "announcement", "官方直连无有效公告，回退镜像源")
    val um = UpdateManager.forPrefs(context)
    // 优先用第一个内置加速源（akaere），而不是保持 null
    val fallbackMirror = um.builtinMirrors().firstOrNull { it.id != "official" }
    val resolved = fallbackMirror?.resolve(URL) ?: URL
    body = fetch(resolved)
}
```

### BUG-4 🟠 HIGH：injectIndexShim 缺少 Content-Type 校验，若拦截范围扩大将损坏 API 响应

**位置**：`MainActivity.kt` → `injectIndexShim()`（第 1379 行）

**问题描述**：
当前拦截范围仅限根路径，所以暂未触发。但一旦按 BUG-1 修复将拦截扩大到所有本地请求，非 HTML 响应（JSON API、CSS、JS 等）也会被拦截：
```kotlin
// 当前代码：无论 Content-Type 是什么，只要匹配路径就注入
val injected = if (html.contains("</head>", ignoreCase = true))
    html.replaceFirst("</head>", storageShimScript + "</head>", ignoreCase = true)
else storageShimScript + html  // ← JSON 响应不含 </head>，脚本会被直接前置，破坏 JSON
```
APIClient 返回 `{"key":"value"}` → 变成 `<script>...</script>{"key":"value"}` → **JSON 解析失败**。

**修复方案**：在 `injectIndexShim` 中增加 Content-Type 前置校验（见 BUG-1 修复方案）。

### BUG-5 🟠 HIGH：engine.log 无限增长，无大小上限，可能导致 OOM 或磁盘耗尽

**位置**：`TerminalView.kt` → `appendLine`（第 95 行）、`MainActivity.kt` → `EngineManager.startEngine`（redirectOutput）

**问题描述**：
- `TerminalView.textView` 累积所有终端文本，永不截断
- `engine.log` 由 `ProcessBuilder.redirectOutput(log)` 直接写入，无任何轮转/截断机制
- 长时间运行或高频日志输出后，TextView 内存占用和日志文件大小持续增长

**修复方案**：
```kotlin
// TerminalView 中增加最大行数限制
companion object {
    private const val MAX_LINES = 2000
}

fun appendLine(text: String) {
    post {
        textView.append(text + "\n")
        // 截断超出最大行数的内容
        val textStr = textView.text.toString()
        val lines = textStr.lineSequence().toList()
        if (lines.size > MAX_LINES) {
            textView.text = lines.takeLast(MAX_LINES).joinToString("\n") + "\n"
        }
        fullScroll(View.FOCUS_DOWN)
        mirrorToLog(text)
    }
}

// EngineManager.startEngine 中：每次启动前截断旧日志
Logs.engineLog(context).truncateTo(50 * 1024) // 50KB 上限，或改用 rotation
```

### BUG-6 🟡 MEDIUM：启动时 APK 更新检查失败会阻断整个应用启动流程

**位置**：`MainActivity.kt` → `startWithApkCheck()`（第 654 行）

**问题描述**：
```kotlin
private fun startWithApkCheck() {
    lifecycleScope.launch {
        apkUpdateManager.checkUpdate(
            onResult = { info ->
                lastUpdateInfo = info
                if (info.hasNew) {
                    presentApkUpdate(info)  // 展示更新弹窗
                } else {
                    startFlowOnce()
                }
            },
            onError = { _ -> startFlowOnce() },  // 虽有 onError 兜底
        )
    }
}
```
`onError` 虽然调用了 `startFlowOnce()`，但存在竞态：如果在 `checkUpdate` 协程尚未完成时用户关闭应用再重新打开，`flowStarted` 的 CAS 可能成功触发重复启动流程。

更严重的是：若 `apkUpdatePending`（强制更新）为 `true`，`onResume` 会持续弹框阻断，用户无法进入应用。

**修复建议**：为 `startWithApkCheck` 增加超时保护（如 10 秒），超时后直接调用 `startFlowOnce()`：
```kotlin
private fun startWithApkCheck() {
    lifecycleScope.launch {
        try {
            withTimeoutOrNull(10_000) {
                apkUpdateManager.checkUpdate(
                    onResult = { info ->
                        lastUpdateInfo = info
                        if (info.hasNew) presentApkUpdate(info) else startFlowOnce()
                    },
                    onError = { _ -> startFlowOnce() },
                )
            }
        } catch (_: TimeoutCancellationException) {
            // 超时：跳过更新检查，直接进入
        }
        if (!flowStarted.compareAndSet(false, true)) return@launch
        startFlowOnce()
    }
}
```

### BUG-7：`clearCache()` 删除整个 cacheDir，可能清除 WebView 缓存的引擎资源

**位置**：`MainActivity.kt` → `clearCache()`（第 1944 行）

```kotlin
cacheDir.listFiles()?.forEach { it.deleteRecursively() }
```
`cacheDir` 是系统分配的缓存目录，WebView 在此缓存引擎的 JS/CSS 资源。清理后下次加载 Web UI 需重新下载，增加启动时间。建议改为仅清理过期文件或限制大小。

---

### BUG-8：`SnapshotExtractor.extract()` 中进度回调精度不足

**位置**：`SnapshotExtractor.kt`（第 72 行）
```kotlin
if (done % (1024 * 1024) < entry.size) onProgress(done, totalBytes)
```
条件判断：`done % 1MB < entry.size`，当 tar entry 很小时（如小文件），可能长时间不回调进度，UI 看起来卡住。建议改为固定间隔（如每 256KB）回调。

### BUG-9：`UpdateManager.checkAndApply` 在更新进行中重复调用时仅输出「更新已在运行」

**位置**：`UpdateManager.kt`（第 167 行）
```kotlin
if (updateRunning) {
    onStage("失败", "更新已在运行")
    return
}
```
用户在更新进行中点击「检查并应用更新」，终端只显示一行失败信息，无法知道当前进度。建议改为复用已有进度显示，或禁用按钮直到更新完成。

### BUG-10：`showUpdateDialog` 的 `cancelable=true` 允许用户通过返回键/点击外部关闭强制更新弹窗

**位置**：`ApkUpdateManager.kt` → `showUpdateDialog()`（第 230 行）

```kotlin
DialogUi.show(
    ...
    cancelable = true,  // ← 强制更新也应不可取消
    onCancel = { if (!forced) onDismissed?.invoke() },
)
```
当 `forced=true` 时，弹窗仍可被返回键或点击外部关闭，此时 `onCancel` 不会触发（因为有 `if (!forced)` 判断），用户可跳过强制更新。应改为：
```kotlin
cancelable = !forced,
```

### BUG-11：`EngineManager.startEngine` 的 `force=true` 绕过了 90 秒冷却，但 `lastStartAttemptAt` 仍被更新

**位置**：`EngineManager.kt`（第 453 行）
```kotlin
if (!force && now - EngineManager.lastStartAttemptAt < START_COOLDOWN_MS) {
    STARTING.set(false)
    return false
}
// ...
EngineManager.lastStartAttemptAt = now  // force=true 时也更新了冷却时间戳
```
看门狗以 5 秒间隔触发，连续失败 3 次（15 秒）后调用 `startEngine(force=true)`。但成功后 `lastStartAttemptAt` 被更新，若引擎随后再次崩溃，在 90 秒冷却窗口内非 force 调用会返回 false。不过因为看门狗只用 `force=true`，影响有限，但逻辑上不够清晰。

### BUG-12：`AndroidBridge.saveSlotConfig` 的键名校验过于宽松，允许含冒号的 key

**位置**：`AndroidBridge.kt`（第 93 行）
```kotlin
if (!Regex("^[A-Za-z0-9._-]+$").matches(key)) return false
```
键名不允许冒号，但 `storageShimScript` 内部使用 `__dshc__m:` 和 `__dshc__p:` 格式作为元数据键。  
如果 dsh Web UI 的某个插件使用包含 `__dshc__` 的 localStorage key，会与 shim 内部键冲突，导致数据错乱。  
建议在 `sanitizeSlot` 或 bridge 层增加保留前缀拦截：
```kotlin
private fun isSafeConfigKey(key: String): Boolean {
    if (key.isEmpty() || key.length > 128) return false
    if (!Regex("^[A-Za-z0-9._-]+$").matches(key)) return false
    if (key.contains("..") || key.contains('/')) return false
    if (key.startsWith("__dshc__")) return false  // 防止与 shim 内部键冲突
    return true
}
```

### BUG-13：`buildWebOverlay` 中 `webView.reload()` 不会重新注入 shim

**位置**：`MainActivity.kt`（第 1604 行）
```kotlin
flatTopButton(I18n.t(this, "刷新", "Refresh")) { webView.reload() },
```
`webView.reload()` 会重新加载页面，但由于 `shouldInterceptRequest` 只拦截主框架请求，子页面刷新（如果有 history API 导航）可能不经过拦截。建议使用 `webView.reloadFromOrigin()` 或确保每次 loadUrl 都经过拦截。

### BUG-14：`SettingsScreen.buildGeneral()` 中「检查引擎」按钮每次创建新线程探测

**位置**：`SettingsScreen.kt`（第 894 行）
```kotlin
Thread {
    try {
        callbacks.onAppendLog(EngineProbe.check().toString())
    } catch (_: Throwable) {
        callbacks.onAppendLog("引擎检查异常")
    }
}.start()
```
`EngineProbe.check()` 是轻量 HTTP 请求（2 秒超时），但每次点击都在新线程执行，无节流。频繁点击会产生多个并发探测请求。建议加 debounce 或复用已有的探测结果。

## 三、低风险 / 建议优化

### BUG-15：`downloadHistoryText` 未做行数限制，长历史记录溢出屏幕

**位置**：`SettingsScreen.kt` → `refreshDownloadHistory()`（第 516 行）

`take(8)` 已限制显示条数，但每条记录可能有多行 detail，整体高度不固定。建议限制 `downloadHistoryText.maxLines = 10` 并加省略号。

### BUG-16：`EnvManager.installLatest()` 的 apt 命令超时无保护

**位置**：`EnvManager.kt`（第 77-82 行）
```kotlin
val cmd = "apt-get update -o Acquire::Retries=3 2>&1; ..."
val pb = ProcessBuilder(bash.absolutePath, "-c", cmd)
```
apt 操作在网络慢或源不可用时可能卡住很长时间（无总超时）。建议给 Process 增加超时销毁逻辑。

---

### BUG-17：` ApkUpdateManager.isApkValid()` 对 APK 头判断过于严格

**位置**：`ApkUpdateManager.kt`（第 77-90 行）
```kotlin
val ver = (head[2].toInt() and 0xff) in 0x03..0x07 || (head[2].toInt() and 0xff) in 0x01..0x02
```
ZIP 文件格式规范中版本字节的有效范围是 0x00-0x33（51 个版本），当前代码只接受 0x01-0x07，可能误拒新版 APK。建议放宽为 `in 0x00..0x33`。

---

### BUG-18：`file_paths.xml` 缺少 `cache-path` 声明，但 `exportDebugLogs` 将日志写到 `filesDir/logs/` 并通过 `files-path` 分享——若将来改用缓存目录分享会 403

**位置**：`app/src/main/res/xml/file_paths.xml`

当前设计将日志放在 `filesDir/logs/` 并通过 `<files-path>` 分享，是正确的。但 `external-cache-path` 声明用于 APK 下载，如果 `getExternalCacheDir()` 返回 null 时会 fallback 到 `cacheDir`，而 `cacheDir` 不在 FileProvider 中声明。建议补充：
```xml
<cache-path name="apk_download" path="." />
```
